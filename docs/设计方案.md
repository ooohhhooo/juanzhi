# Primary School English Exam Knowledge-Point Analysis Workbench: Design Plan v0.1

> 2026-10-25. Distilled from three research reports (competitor workbenches, cross-platform architecture, front-end interaction).
> Model assignments:
> - Research: Opus 5.5
> - Coding: Opus 4.6
> - Review: Sonnet 5.5
> - Image generation: Codex

## 1. Product scope

- **Users**: primary school English teachers and teaching researchers. They are not technical, so they should be able to download it and use it without logging in.
- **Data**: everything is stored locally on the user's machine. There is no server and no cloud database.
- **Inputs**: school exam papers. Supported formats are PDF (both text-based and scanned), images (JPG/PNG/HEIC), and Word (.docx).
- **Outputs**:
  - Knowledge-point distribution for each grade
  - Exam frequency, plus key and difficult points
  - Year-over-year comparison (2026 school year vs. earlier years): newly added, dropped, rising, and falling knowledge points
  - AI-written analysis for newly added points, shown with screenshots from the original papers
  - A list of frequently tested points to watch out for
  - An AI exam-trend analysis report, exportable as Markdown or PDF
  - A two-way specification table, exportable as Excel/CSV
- **Platforms**: macOS (Apple Silicon + Intel) and Windows 10/11 x64.

## 2. Architecture decisions

| Item | Choice | Reason |
|---|---|---|
| App framework | **Electron 45** + React 19 + TypeScript + Vite | One codebase produces both Mac and Windows builds. No Rust install needed. Chromium renders identically on both platforms. |
| Database | **`node:sqlite`, built into Node 24** (bundled with Electron 45) | No native modules, so the Windows build can be cross-packaged from a Mac. Fallback is sql.js. On day one, verify inside the Electron main process that `require('node:sqlite')` actually works. |
| UI | Ant Design 6 + ECharts 6 | Mature Chinese-language components. Tree selectors, tables, and upload are all built in. ECharts covers treemaps and heatmaps. |
| Data caching | TanStack Query | Whenever the main process pushes a `data:changed` event, the relevant queries are invalidated by entity type, so new papers show up on the dashboard immediately. |
| PDF | pdfjs-dist, used in the renderer process on both platforms | Extracts the text layer and renders pages to PNG. The code is identical on both platforms, so it can be tested on a Mac. |
| Word | mammoth (text) + zip extraction of `word/media` (images) | Pure JS, cross-platform. |
| OCR | Mac: a bundled Swift command-line tool using the Vision framework. Windows: Windows.Media.Ocr called through PowerShell 5.1. Fallback: vision models (deepseek-flash / qwen3-vl-plus). | The system OCR is offline and free. On Mac it has been tested: two pages took 1.7 seconds, and Chinese and English were recognized accurately. If the Windows Chinese language pack is missing, the app automatically falls back to the vision model. |
| AI | OpenAI-compatible interface. Users enter their own base_url, model, and API key. | Presets are built in for DeepSeek (deepseek-flash / deepseek-v4-pro), Qwen, Doubao, Kimi, and Zhipu. The API key is encrypted with `safeStorage`. |
| Packaging | electron-builder. Mac: dmg (arm64 + x64), ad-hoc signed. Windows: NSIS installer + portable build, built on GitHub Actions. | No signing certificate needed. The install guide explains how to open the unsigned app. |

### OCR layering (same for both platforms)

1. **Text layer first**: for text-based PDFs (pdf.js) and Word files, take the text directly. In parallel, render each page as an image for screenshots.
2. **System OCR**: if a page has no text layer, or very little text, run the page image through system OCR (Mac Vision / Windows OCR). This returns line coordinates.
3. **Vision-model fallback**: if OCR confidence is low, or the system OCR is unavailable, send the page image to a vision model and use the "vision version" of the P1 prompt.

### Data directory

The default data directory is `app.getPath('userData')/workbench-data/`, and the location can be changed in Settings. Layout:

```
workbench-data/
  db.sqlite
  files/<paperId>/original.<ext>       original paper
  files/<paperId>/page-<n>.png         rendered page images
```

### Moving data between computers

- **Export**: produces a `.ewb.zip` package containing:
  - a database snapshot made with `VACUUM INTO`
  - the `files/` folder
  - `manifest.json` (schema version, export time, paper count)
- **Import**: choose either "overwrite" or "merge"; merging dedupes by UUID.
- The API key does not go in the data package. It must be re-entered after switching computers.

## 3. Data model (SQLite)

- **papers**: one row per paper.
  - id(uuid), title
  - grade(1-6), semester(上/下)
  - school_year_start: an integer, e.g. 2025 means the 2025-2026 school year (the "2026" shorthand)
  - exam_type: unit test / midterm / final / monthly test / other
  - textbook, region, school, total_score
  - file_name, file_hash: the same file imported twice triggers a warning; the user may choose "import anyway" (no UNIQUE index). `duplicate_of` stores the id of the paper it duplicates, so statistics can exclude or flag it.
  - status: imported / extracting / **extracted** / parsing / reviewing / done / failed. Flow: `imported → extracting → extracted → parsing → reviewing → done`; any stage can end in `failed`. `reviewing` = parsed by AI, waiting for the teacher; `done` = the teacher confirmed the whole paper (editing a question of a `done` paper moves it back to `reviewing`). A `failed` paper carries `error_stage` (`extract` or `parse`): a parse failure keeps all extracted pages (and any earlier questions) so it can be retried from the queue without re-extracting. An interrupted `parsing` job returns to `reviewing` if the paper already has questions, otherwise to `extracted`.
  - error (only for `failed`), error_stage, warning (non-fatal notes on an `extracted` paper, e.g. "N pages had no text", "OCR failed: ..."), page_count, extracted_at, ai_model (text model, or `text + vision` when both were used), created_at
  - M2 additions: prompt_version (e.g. `v1.1`, or `v1.1+自定义·<hash>` when the user edited the prompts), parse_stage (prepare / ai / locate / save / done), parsed_at, ai_meta_json (JSON array of the metadata fields the AI pre-filled, shown as "AI guess" until the user edits that field's value)
- **pages**: paper_id, idx, image_rel (empty for docx), width, height, lines_json (lines with normalized 0-1 coordinates, top-left origin; empty when there are no real coordinates — never fabricated).
  - text_source: `pdf-text` (PDF text layer, passed the quality gate) / `ocr` (local OCR) / `docx` (Word text) / `vision` (vision model, M2) / `needs_ocr` (this platform has no OCR) / `ocr_failed` (OCR did not run successfully; reason in `ocr_error`) / `none` (OCR ran fine, the page really has no text).
  - text (verbatim text; for `pdf-text` pages this is the PDF text layer the parsing step anchors on), ocr_conf, ocr_error, text_layer_chars (size of the PDF text layer, for diagnosing).
  - Text-layer quality gate: a text layer is trusted only if it has at least 50 visible characters, at least 80% readable characters and under 5% private-use / U+FFFD characters. Otherwise the page goes to OCR.
- **paper_assets**: images extracted from a docx (`files/<paperId>/media/<n>.<ext>`): paper_id, page_idx, seq, rel_path, mime, bytes. The page text holds `[图n]` placeholders in the original position.
- **questions**:
  - id, paper_id, ord (1-based position in the paper, contiguous), no_label (the authoritative question number as printed: "21(1)", "~1"; the legacy `no` INTEGER column is kept but only filled when the label is numeric), section, section_title, qtype, material_id (→ materials.mid)
  - stem, options (JSON array), answer (printed reference answer only, never solved by the AI), score
  - difficulty(1-5, estimated), error_prone, error_reason
  - page_idx, bbox_json (normalized [x,y,w,h], from the question's start down to just before the next question), bbox_source (`text-anchor` / `vision` / `manual` / `none`), anchor, anchor_ref
  - confidence (computed by the program from flags and locating result, not self-reported by the model; < 0.7 is highlighted for review), reviewed, edited (the teacher changed the content), flags_json
  - kp_suggestion (the AI's proposal for a knowledge point missing from the tree, or `待归类：<code>` when it returned an unknown code), kp_suggestion_status (`pending` / `approved` / `rejected`). Suggestions never touch the tree by themselves; approving one in the review page creates the node.
- **question_kps**: question_id, kp_code, is_primary.
- **kps (knowledge-point tree)**: code (stable ID such as `GR.TENSE.PAST`), parent_code, name, level (1–3), intro_grade, sort, deprecated, merged_into, note (explanation / example words, injected into the prompt), builtin (1 = shipped seed, 0 = created by the teacher). The seed is migration v5 (`KP_SEEDS_V1`, frozen); later seed updates must be new migrations that only touch `builtin = 1` rows the teacher has not edited.
- **qtypes (question types)**: code, name, group (listening / written), note, sort, builtin. Always contains the `OTHER` fallback.
- **materials**: paper_id, mid (`b<batch>-m<n>`), section, kind (passage / dialogue / word_bank / listening_script / table / other), text, page_idx. Questions reference them by `material_id`.
- **parse_runs**: one row per AI parse: paper_id, prompt_version, model, vision_model, status (`running` / `ai_done` / `done` / `failed` / `cancelled` / `interrupted` / `superseded`), error, result_json (the merged AI result, so "re-locate only" can run without calling the model; cleared when the paper is re-extracted), usage_json, started_at, finished_at.
- **ai_usage**: paper_id (deliberately no foreign key: cost statistics survive paper deletion), kind, model, prompt_tokens, completion_tokens, cached_tokens, ok, created_at.
- **reports**: id, kind (yearly / report / kp), filter_json, markdown, model, created_at.
- **ai_analyses** (M3, migrations v6–v8): the cache of the P2 year-over-year analysis, one row per "comparison scope" (the filter that actually applies on the comparison page — the school-year filter is dropped, the comparison picks its own years — plus target year, baseline, knowledge-point level and whether semester alignment is on; `scope_key` = hash of that, primary key; regenerating overwrites the row). `cache_key` = hash(scope, system prompt text, the user prompt text with all the data filled in) — i.e. **the text actually sent to the model**, not a hand-maintained version number; any change in the prompt template, the numbers or a sample question's stem changes it. If the current `cache_key` differs from the stored one the result is shown as **stale** ("已过期，可重新生成", with the reason: data / prompt template / model changed); it is never regenerated automatically. Also stores `markdown`, `refs_json` (the `[试卷标题 · 题号]` citation index), `warnings_json`, `model`, `usage_json`, `fingerprint` (hash of the filled placeholders = the data part), `template_sig` (hash of the system + user templates = the prompt part). To avoid recomputing the whole P2 input on every read, the row also keeps `checked_rev` / `checked_sig` / `checked_json` (the data revision and template signature at the last check, and its verdict): the verdict is reused while both are unchanged. v6 also adds indexes `question_kps(kp_code)`, `papers(status, school_year_start)`, `questions(paper_id, qtype)`.
- **data_rev** (M3, v7/v8): one row, a monotonic *data revision* number bumped by triggers whenever something that can change the statistics is written: `papers` rows that are (or just stopped/started being) `done`/`reviewing` and whose statistics-relevant columns (status, grade, semester, school_year_start, exam_type, textbook, region, file_hash, created_at, title) change, their `questions` and `question_kps`, and any change to `kps` / `qtypes`. Import progress of papers that are not counted does not bump it.
- **settings**: key, value_json. The generic `settings:get/set` IPC only accepts an allow-list (`data_dir_custom`, `ui_theme`, `ui_language`, and M3's `ui_stats_filter` = the global filter bar's last state). AI configuration (`ai_config`, no secret), the encrypted API key (`ai_key_enc`, `safeStorage`) and prompt overrides (`ai_prompts`) are only reachable through the `ai:*` IPC, and no IPC returns the key.

## 4. Statistics conventions (to avoid misleading numbers)

- **Which papers are counted**: by default only papers with status `done` (confirmed by the teacher); an explicit switch adds `reviewing` (AI result not yet confirmed) and the UI then shows a prominent warning. `failed`/in-progress papers are never counted.
- **Duplicates**: the same file imported several times (same `file_hash`) counts **once** by default. Among the copies visible under the current status and filter, the representative is chosen **`done` first, then earliest imported**; so a confirmed copy still stands in when the original is unconfirmed or has been deleted, and a paper never vanishes just because it is a "copy". A switch "include duplicates (counted repeatedly)" counts every copy. Every page shows how many copies were merged.
- **Year-over-year is semester-aligned by default**: a school year has two semesters and the current one is usually only half done, so the baseline only takes papers from the semesters that appear in the target year (the two sides' semester make-up is shown side by side); a switch turns alignment off, in which case a "semester make-up differs" warning is shown because knowledge points taught only in the missing semester would otherwise look "new" or "dropped". The P2 prompt's filter description states the semester range. The baseline-year list handed to the model only contains years that actually contributed papers after alignment, and the knowledge-point drawer lists question cards from exactly the same baseline scope as the table.

- **Appearance rate** = number of papers containing the knowledge point ÷ number of papers in the current filter. This is the main metric. Raw "question count" is not compared across years, because different years have different numbers of papers.
- **Point share** = total points for questions on that knowledge point ÷ total points.
- **Difficulty** and **error-prone** are AI or teacher estimates and must be labeled "estimated" in the UI. With no student scores, there is no statistical difficulty and no score rate.
- **Year-over-year comparison**: target school year vs. baseline (all earlier years by default, or one specific year).
  - Newly added: appearance rate in the target year > 0, and 0 in the baseline.
  - Dropped: the reverse.
  - Rising / falling: change in appearance rate ≥ 20 percentage points.
  - If either side has fewer than 5 papers, show a "limited sample" warning.
  - Textbook revisions: the new PEP edition is replacing older books year by year. Show the textbook-version distribution side by side, and let the AI distinguish "textbook change" from "a change in question-setting approach".
- **Two-way specification table**: knowledge point × question type, with cells showing question count / points.

## 5. Pages and interaction (from the front-end design report)

The left sidebar can be collapsed. A global filter bar stays fixed at the top: grade, semester, school year, exam type, textbook, region. Filters are remembered after a restart.

1. **Overview**
   - Number cards: papers / questions / knowledge points / awaiting review
   - Top 10 frequently tested points
   - Points newly added this school year
   - Recent imports
2. **Paper library**
   - School year / grade tree on the left, table on the right
   - "Import papers" accepts drag-and-drop of multiple files
   - The AI pre-fills metadata from the paper header, and the user confirms it
3. **Processing queue**
   - Per-paper stage steps: extract → split into questions → tag → save to database
   - A failed paper can be retried from the stage where it failed
   - 2 papers run concurrently
4. **Review** (three columns)
   - Left: question list, with low-confidence items highlighted in yellow
   - Middle: the original page, with the current question's box highlighted
   - Right: the tagging form (knowledge-point tree selector, question type, difficulty, points, error-prone)
   - Shortcuts: J/K to move between questions, Enter to confirm
5. **Analysis dashboard**, in three tabs
   - **Distribution**: knowledge-point treemap you can drill into, exam-frequency bar chart, question types, difficulty, two-way specification table
   - **Year-over-year comparison**: four columns for newly added / dropped / rising / falling. Clicking a point opens a drawer with the AI analysis, question cards, and screenshots from the original paper. Clicking a screenshot opens the full original page.
   - **Key and difficult points**: ranked by appearance rate × point share × error-prone
6. **AI report**
   - History list
   - Generated with live streaming output
   - Export to Markdown / PDF
7. **Settings**
   - AI service (presets, connection test)
   - Prompts (editable, can be reset to defaults)
   - Knowledge-point tree (edit, merge, rename; keeps the stable ID)
   - Data directory and export/import of data packages
   - About and install guide

**First launch**: three step cards: set up AI (can be skipped, in which case tagging is manual only), drag in your first papers, choose a textbook version. A "Load sample data" button lets users try the app first.

### IPC (renderer → main, via preload `window.api`; params validated with zod)

| Module | Methods |
|---|---|
| Papers | `papers.import(paths, {allowDuplicates?})` (registers and returns at once; extraction runs in a background queue; duplicates come back with `code:'duplicate'` for the UI to confirm), `papers.update(id, meta)` (a field set to `null` is cleared), `papers.list(filter)`, `papers.get(id)`, `papers.pages(id)`, `papers.assets(id)`, `papers.remove(id)`, `papers.reprocess(id, fromStage?)` |
| Questions | `questions.list(paperId)`, `questions.update(id, patch)`, `questions.split`, `questions.merge` |
| Statistics | `stats.overview(filter)`, `stats.distribution(filter)`, `stats.compare(filter, target, base, level?)` (`base` = `'before'` or a school year), `stats.hot(filter, level)`, `stats.matrix(filter, level)`; M3 additions: `stats.questions(filter, side, code, limit?)` (question cards for the drawer), `stats.filterOptions(filter?)`, `stats.exportMatrix(filter, level)` (save dialog + CSV). All parameters validated with zod (`.strict()` filter objects); every number is aggregated in SQL in the main process. |
| Knowledge points | `taxonomy.tree()`, `taxonomy.save(ops)` |
| AI | `ai.test(cfg)`, `ai.compareAnalysis(scope)` (read the cache state, never spends tokens), `ai.analyzeCompare(scope, requestId)` (streaming; deltas arrive as `ai:chunk` events sent only to the window that made the request; the call's return value repeats the final outcome, including any partial text), `ai.cancel(requestId)`, `report.generate(filter)` (streaming, M4), `report.export(id, fmt)` (M4) |
| Settings and data | `settings.get/set` (key allow-list), `ocr.status()` (helper present? language pack?), `data.exportPack()`, `data.importPack(path, mode)`, `data.chooseDir()` |
| Events | `job:progress`, `data:changed` (batched every 500ms; `papers`/`questions`/`taxonomy`/`materials`/`pages` invalidate the dashboard's `['stats']` queries), `ai:chunk` (`{id, type: start/delta/reset/done/error/cancelled, …}`; `reset` = a retry is starting, discard what you showed) |

**Import paths** are only accepted when they come from the open-file dialog or from the preload's `getPathForFile` on a real dropped `File` (the preload registers them with the main process; the page's own scripts cannot). Dropping files anywhere in the window imports them; the window never navigates away from the app's own entry page.

**Images**: displayed through custom protocols. `ewb://page/<paperId>/page-<n>.png` serves page images and `ewb://media/<paperId>/<n>.<png|jpg|gif>` serves docx images; both accept whitelisted file names only and the main process checks that the resolved path stays inside the data directory (originals are never served). `ewb://pdfjs/...` is internal (CMap and standard-font data for the hidden PDF render window). Screenshot crops are done in the front end with CSS positioning. For export, the main process uses `nativeImage.crop` to produce the actual crop images.

## 6. Fixed prompts

- v0 draft: [prompts/v0-示例草稿.md](prompts/v0-示例草稿.md)
- Sonnet 5.5 rewrite: `prompts/v1-sonnet改写.md`

There are 4 prompts in total:
- **P1 parsing, text version**: split into questions + tag; JSON output; `anchor` is copied verbatim from the original text and used to locate the question for screenshots
- **P1 parsing, vision version**: reads the page images and returns bboxes
- **P2 year-over-year analysis**: the model does not compute statistics; it only interprets them, and it distinguishes textbook changes from changes in question-setting approach
- **P3 exam-trend report**

The knowledge-point list is injected into the prompt at runtime from the knowledge-point tree (`{{KNOWLEDGE_TREE}}`), and the AI may only choose from existing codes.

## 7. Built-in knowledge-point tree (first version, editable)

Built on Appendix 4 (grammar items) of the curriculum standard + the theme tables + the PEP textbook. Three independent dimensions: knowledge point / question type / theme.

| Level 1 | Level 2 examples (code) |
|---|---|
| Phonics PH | Letter recognition PH.LETTER, letter sounds and phonics PH.PHONICS (vowels, consonants, letter combinations), stress and intonation PH.STRESS |
| Vocabulary VO | Theme vocabulary VO.TOPIC (school, family, food, clothing, weather, animals, time…), word-form changes VO.FORM, set phrases VO.PHRASE |
| Nouns GR.NOUN | Singular/plural (regular / irregular), countable vs. uncountable + some/any, possessive case |
| Pronouns GR.PRON | Personal pronouns (subject / object), possessive pronouns (adjectival / nominal), demonstratives this/that/these/those |
| Numerals GR.NUM | Cardinal numbers, ordinal numbers, time expressions |
| Prepositions GR.PREP | Place (in/on/under/next to/behind), time (in/on/at), set phrases (time for/to) |
| Verbs / modals GR.VERB | be verbs, have/has, can/can't, should/must, Let's / imperative sentences |
| Tenses GR.TENSE | Present simple (incl. third-person singular), present continuous, past simple (regular / irregular), future simple (be going to / will) |
| Adjectives / adverbs GR.ADJ | Comparatives (regular / irregular), introductory superlatives, frequency adverbs |
| Sentence patterns GR.SENT | There be, yes/no questions and short answers, wh-questions (what/where/how much/what time…), exclamatory sentences |
| Functional communication FN | Greetings, shopping, asking for directions, weather, time, suggestions and invitations |
| Reading RD | Detail comprehension, inference and judgment, main idea |
| Writing WR | Joining words into sentences, writing about pictures, written expression (by tense / topic) |

**Question types**:
- Listening (6 types)
- Phonics comparison PH_DIFF
- Choose the odd one out VO_CLASS
- Look at the picture and choose / write the word
- Multiple choice MC
- Fill in with the correct form FORM
- Match sentences
- Complete the dialogue DIALOG
- Cloze
- Reading true/false RD_TF
- Reading multiple choice RD_MC
- Join words into sentences ORDER
- Written expression WRITE

## 8. Testing plan (no Windows machine available)

1. **Development on Mac**: all logic outside OCR (pdf.js / database / statistics / AI / UI) uses the same code on both platforms, so it can be fully tested on a Mac.
2. **GitHub Actions `windows-latest`**: on every commit it builds the exe and uses Playwright to drive Electron through a smoke test: launch → import sample paper → OCR → dashboard has data → screenshots uploaded as artifacts.
3. **(Optional) UTM + Windows 11 ARM virtual machine**: for manually checking UI and fonts; the ISO is available free from Microsoft.
4. **Before release**: one round of acceptance on the user's real Windows computer, using a 10-item checklist.
