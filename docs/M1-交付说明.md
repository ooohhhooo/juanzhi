## 1. 技术栈（实际安装版本）

Electron 45.0.0（Node 24，内置 `node:sqlite`，**无任何原生模块**）· React 19.3.1 · antd 6.6.7 · electron-vite 6.0.0 / vite 6.4.5 · TypeScript 5.9.3 · pdfjs-dist 4.10.38 · mammoth 1.13.0 · jszip 3.10.2（直接依赖，用于体检 docx 文本框）· zod 3.25.76 · @tanstack/react-query 5.104.5 · react-router-dom 7.18.4。
开发依赖：`playwright-core 1.64.1`（只用来驱动真实 Electron 做 E2E，不下载浏览器）。

## 2. 怎么跑

```bash
export npm_config_cache=$TMPDIR/npmcache
npm run dev            # 开发
npm run build          # 构建 main / preload / renderer
npm run typecheck      # node + web 两套 tsconfig
npm run test:unit      # 单元/静态校验：ocr.ps1（BOM、正则行为、显式结果类型）、文本层质量门
npm run test:e2e       # 构建后用 playwright-core 启动真实 Electron，跑 52 项检查（需在沙箱外，约 3 分钟）
bash scripts/build-ocr-mac.sh   # 重新编译 macOS OCR/图片转换通用二进制（arm64+x86_64）
```

数据目录固定为 `~/Library/Application Support/english-exam-workbench/workbench-data/`（Windows：`%APPDATA%\english-exam-workbench\workbench-data\`），`dev` / `build` 后运行 / `electron .` 都一致。
`EWB_USER_DATA_DIR` 只给自动化测试隔离数据，`EWB_PRINT_USERDATA=1` 只让应用打印数据目录就退出（E2E 用它验证默认路径而不触碰真实数据库），正常使用不要设置。

## 5. Windows OCR 脚本（⚠️ 从未在 Windows 上运行）

`native/windows/ocr.ps1`：PowerShell 5.1 + `Windows.Media.Ocr`。`-Check` 只探测引擎与语言；识别时 stdout 只输出一段 JSON（含 `lang`）。退出码 1 读图/识别失败/尺寸超限、2 类型加载失败、3 没有 OCR 语言包。要点：UTF-8 **带 BOM**（PS 5.1 对无 BOM 脚本按 GBK 读）；正则用纯 ASCII 的 `\uXXXX`；语言先 `zh-Hans-CN` 再用户语言，回退到非中文引擎时主进程会在试卷警告里提示；坐标用 `Words.BoundingRect` 合并后归一化；置信度固定 0.8。
**静态校验（`npm run test:unit`）能证明的**：BOM 在、正则纯 ASCII 且行为正确（含对旧写法的对照）、不再用 `GetInterfaces()` 推断。**证明不了的**：WinRT 类型加载写法（程序集提示）、`AsTask` 反射、`-Check` 的输出、组策略/约束语言模式下反射是否可用。
人工验收清单（Win10 1809+/Win11）：`powershell -NoProfile -ExecutionPolicy Bypass -File native/windows/ocr.ps1 -Check` 输出 `{"lang":"zh-Hans-CN"}`；对 `samples/g4-2025-page1.png` 跑一次，stdout 只有一段合法 JSON、行数 >30、中文无乱码且汉字间无多余空格。建议用 GitHub Actions `windows-latest` 跑（设计文档第 8 节本来就有这个计划）。
